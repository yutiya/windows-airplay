## 需求：Windows 平台 Electron + Node.js 的 iPhone AirPlay 投屏应用（免费开源）

用户要求先分析实现路径、确认需求后再开发。本轮只做技术调研，未创建任何代码或项目文件。

### 调研结论
- 纯 Node.js/Electron 无法实现 AirPlay 接收端；核心协议栈（mDNS/DNS-SD 发现、RTSP/HTTP 信令、pair-setup/pair-verify 配对、FairPlay 解密、RTP 收流、H.264 解码、音视频同步）必须是 C/C++ 原生进程。
- 推荐架构：Electron 负责 UI/设置/托盘/进程守护 → Node 主进程 spawn UxPlay → GStreamer（d3d11videosink + wasapisink）渲染 → Win32 `SetParent` 把 GStreamer 视频窗口 HWND 嵌入 Electron 内容区。Electron 完全不碰解码，规避其 H.264 编解码/专利构建不确定性。
- 可复用项目：
  - UxPlay 1.73.x（GPLv3，活跃维护，支持 Win10/11 + AirPlay 2 镜像，MSYS2/MinGW + GStreamer 构建，需 Bonjour SDK；1.73 新增 `-vrtp` 输出解密 H.264/H.265 RTP、BLE beacon 发现）。
  - Spieglein（GPLv3，Microsoft Store 上架，WinUI3 + UxPlay + mDNSResponder，已验证 `SetParent` 嵌入方案，运行时约 250MB）。
  - uxplay-windows（GPLv3，Windows 运行时打包范式：预编译 uxplay.exe + GStreamer DLL + mDNSResponder + 安装包）。
  - winplay（Electron + UxPlay，方向最贴合但不成熟：要求用户自装 MSYS2/Bonjour SDK，License 仅写 "licensed free" 不规范）。
  - RPiPlay / airplay2-receiver：前者是 UxPlay 前身，后者仅音频，均不适合直接做镜像接收端。
- 许可证约束：UxPlay 为 GPLv3，分发二进制时整体需 GPLv3；若想 MIT/Apache 需做进程隔离（arm's length 通信），法律上存在争议。
- 已知边界：DRM 内容（Netflix/Apple TV+）不可镜像；部分 iOS 游戏不传音频；不支持 AirPlay 2 多房间音频；iOS 升级可能破坏协议需跟随上游；需同局域网 + 专用网络 + 防火墙规则；无代码签名会触发 SmartScreen/杀软误报；延迟为数百毫秒级。
- 可选进阶：UxPlay `-vrtp` 把解密 RTP 交给自研渲染器，UI 更灵活、便于录屏，但要自行处理音频、remux 与 Electron 侧解码，复杂度高，建议 P2 之后。

### 许可证冲突与处置（重要）
MIT/Apache 与 UxPlay 的 GPLv3 存在张力。结论：自用不分发时 GPLv3 的源码提供义务不触发，现阶段可按 MIT 写主程序；但必须按强隔离设计，为将来公开分发留余地：
- UxPlay 作为独立、可替换的 exe 外部依赖，不 vendoring 源码、不静态链接、不 N-API 链接；通过 `UXPLAY_PATH` 配置定位。
- 进程间只用命令行参数 + stdout/stderr + 退出码通信；不共享内存、不共享内部数据结构。
- 预留 THIRD_PARTY_NOTICES.md：GPLv3 全文、UxPlay 版权声明与源码获取方式、GStreamer LGPL 动态链接与可替换说明、mDNSResponder Apache/BSD 声明。
- 灰色地带：FSF 对「专为某 GPL 程序设计并捆绑分发」判定较严；SetParent 对 UxPlay 的 GStreamer 窗口做跨进程控制会强化「一体化」印象。公开发布前需正式法律复核，或整体切回 GPLv3（Spieglein 的做法）。此为非正式法律意见。

## 修复：首次 iPhone 连接黑屏、断开重连才正常（用户真机反馈）

用户真机测试反馈：第一次屏幕镜像时日志出现 `Begin streaming to GStreamer video pipeline`，但应用窗口一直没画面；停止镜像后再连接就正常。
根因分析：视频窗口是 GStreamer 在**第一次连接**才创建的；旧 `watch()` 一检测到窗口就立即 `SetParent`，且 `embed()` 先改窗口样式（WS_POPUP→WS_CHILD）再换父窗口、缺少 `SWP_FRAMECHANGED`，在 D3D11 videosink 完成 swapchain 初始化前触发窗口重建，打断首次渲染。`-nc` 保留窗口，所以第二次连接复用已稳定的子窗口才正常。日志「Begin streaming…」证明引擎端管线已在推流，问题在显示/嵌入侧。

修复（已落地，待用户复测）：
- `winembed.js`：`embed()` 改为先 `SetParent` 再改样式，新增 `SetWindowPos`（带 `SWP_NOZORDER|SWP_NOACTIVATE|SWP_FRAMECHANGED|SWP_SHOWWINDOW`）与 `InvalidateRect`；新增 `nudge()` 温和校正（重发几何 + 请求重绘，不换父窗口）；`watch()` 增加稳定期（同一 hwnd 且尺寸不变持续 `settleMs`，默认 1500ms，可 `shouldEmbed` 提前放行、maxWaitMs 8000 兜底）与候选窗口日志。
- `uxplay.js`：`_onLine` 检测 `Begin streaming to GStreamer video pipeline` → emit `pipeline-ready`。
- `config.js`：新增 `embedDelayMs: 1500`。
- `index.js`：新增 `pipelineReadyAt`、`scheduleNudges()`（250/900/2000ms 三次校正）、`reembed()`（detach + 重新嵌入）；`startWatching(pid, forceImmediate)` 传稳定期与 shouldEmbed；IPC `app:reembed`；托盘加「重新嵌入画面（黑屏时用）」。
- UI：工具栏「重嵌画面」按钮、设置里「画面嵌入延迟（毫秒）」；preload 加 `reembed`。README 新增「首次连接黑屏（已修复）」章节。

验证：全量 JS 语法通过、koffi FFI 自检正常、`npm run check` 12 项全过；应用已重启加载修复。真机复测仍由用户进行；若仍黑屏，日志面板的 `[画面] 发现视频窗口 … / 已嵌入（等待 Nms）/ 正在校正视频窗口` 可继续定位，或调大 embedDelayMs / 点「重嵌画面」。

## 第二轮：首次连接黑屏仍未解决，改为「不换父窗口」的覆盖模式

用户真机复测反馈：第一轮修复后**第一次投屏仍然黑屏，必须停止再投屏才出画面**。因此否定「只是嵌入时机太早」的判断，改判断为：`SetParent` 把顶层 `WS_POPUP` 变成 `WS_CHILD` 本身会让 D3D11 swapchain 失效，且首次连接的 pipeline 不重建它；第二次连接 pipeline 重建才恢复。上游 uxplay-windows 2.0 的 Known Issues 也明确写了「首次连接画面冻结，重连一次就好」，可能部分原因在引擎侧。

实现三种可切换模式（`config.embedMode`，默认 `owned`）：
- `owned`：**不 SetParent、不改样式**，用 `SetWindowLongPtrW(GWLP_HWNDPARENT=-8, Electron HWND)` 建立 owner 关系（窗口仍是顶层、D3D11 不受影响），再用 `SetWindowPos(SWP_NOZORDER|SWP_NOACTIVATE|SWP_SHOWWINDOW)` 按 `videoScreenRect()`（getContentBounds × scaleFactor + 工具栏偏移）定位到 Electron 内容区。
- `child`：原 SetParent 嵌入，保留作对照。
- `detached`：完全不干预，视频窗口独立显示 —— 关键对照实验，若独立窗口第一次就有画面即可确认问题在嵌入侧；若也没有，则是引擎自身 bug。

配套：`winembed.js` 新增 `attachAsOwned/repositionOwned/detachOwned`，`watch()` 增加 `release` 回调（不同模式清理方式不同）并把**全部候选窗口**传给 onCandidate；`index.js` 新增 `videoScreenRect()`、`persistLog()`（日志落盘 `%APPDATA%\free-airplay-receiver\engine.log`）、IPC `app:open-log`、切换 embedMode 后自动 reembed；UI 加「画面嵌入模式」下拉与日志面板「打开日志文件」按钮；preload 加 openLog；README 同步。

日志现在会记录候选窗口列表（hwnd/class/尺寸）、选中项、等待时长、模式与校正时间，下一轮若仍黑屏可直接读 `engine.log` 定位，不必再靠截图猜。验证：全量 JS 语法、koffi FFI、`npm run check` 12 项均通过；真机复测待用户进行。

## 第三轮：落盘日志 + 窗口枚举找到真正根因（隐藏的视频窗口）

用户第二次真机复测：第一轮/第二轮修复后**第一次投屏仍黑屏，必须停止再投才出画面**。
新增的日志落盘（实际路径是 `%APPDATA%\免费投屏\engine.log`，因为 package.json 的 productName 是中文；README 旧路径 `%APPDATA%\free-airplay-receiver\` 是错的，已全量修正）给出了决定性证据：日志里有 `Begin streaming to GStreamer video pipeline`、`found window to rename, setting new name...`、真实 iPhone 连接记录（`iPhone12,1 / AirPlay/406.31.21 / AAC-ELD 44100/2`），但**整份日志一次 `[画面] 候选窗口 N 个` 都没有** → 窗口枚举从没找到视频窗口，前两轮调的 SetParent/owner/延迟逻辑一次都没执行到！用户第二次看到的画面其实是 Qt 引擎自己弹出的独立窗口，并非应用嵌入结果。

用 koffi 写全量窗口枚举（顶层 + EnumChildWindows）得到 Qt 引擎 PID 9296 的窗口：
```
hwnd=4916958 pid=9296 visible=false 516x1100 class=GstD3D12Hwnd title="AirPlay Video Stream"
```
其余是 Qt6101TrayIconMessageWindowClass / ThemeChangeObserverWindow / ScreenChangeObserverWindow / IME。视频窗口是顶层窗口但**创建后是隐藏的**（D3D12 sink 等首帧才显示），而旧 `windowsOfPid()` 有 `IsWindowVisible` 硬过滤，直接把它筛掉了。另外注意 Qt 引擎实际用 D3D12 sink（类名 GstD3D12Hwnd），说明 arguments.txt 里的 `-vs d3d11videosink` 被 Qt 引擎忽略。

修复：`windowsOfPid()` 不再按 visible 过滤，新增 `GetWindowTextW` 取标题并返回 visible/title 字段；新增 `candidateWindows(pid)` 按评分选窗口（类名/标题含 gstd3d|gstreamer|airplay video|video stream 加 1e8；Qt 托盘/观察者窗口减 1e8；可见加 5e7），`pickVideoWindow` 与 `watch` 共用它；三种模式都主动 `ShowWindow(SW_SHOW)`（detached 分支也补上，否则独立窗口仍是隐藏的对照不了）；onCandidate 日志加 visible/title/全部候选明细。
经验教训：**遇到「嵌入不生效」先确认枚举到底有没有找到窗口，不要先调嵌入时机**。真机复测待用户进行。

## dev 分支（基于 v0.0.1）：当前窗口内显示 + 投屏背景色 + 首次投屏保护

用户要求：基于 v0.0.1 建 dev 分支继续开发；连接成功后就在当前窗口显示共享内容、不再另开窗口；投屏时改背景色突出内容；同时确保「第一次投屏没画面、要等第二次」不再出现，开发完要再检测。

关键判断（重读 engine.log 13:20 段）：v0.0.1 默认 `owned` 模式虽然把独立视频窗口定位到应用内容区，但窗口本质仍是顶层 `WS_POPUP`，用户在第二次连接看到的画面就是引擎自己弹的独立窗口 —— 这正是「又创建新窗口」的来源。而首次连接日志里 `[画面] 已嵌入` 确实执行过却仍无画面，说明不只是嵌入时机问题，还要在显示链路上加保障。

实现：
- `git checkout -b dev v0.0.1`；v0.0.1 是精简分支（runtime 不入库），用 `git checkout master -- runtime` + `git reset -- runtime` 把 477MB 运行库还原成 dev 下被 .gitignore 忽略的本机文件，保证仍能起引擎验证。
- 默认 `embedMode` 改 `child`（SetParent 真嵌入）；`config.js` 加 `CONFIG_VERSION=2` 迁移，旧 `owned`/1500ms 一次性升级为 `child`/600ms，用户显式选过的其它模式不动。
- `geometry.js` 新增 `fitRect()`：按源宽高比居中、四周留 10 CSS px 取景框；`streamBgColor` 默认 `#000000`，`body.streaming` 时切换 `#stage` 背景（顺带修掉竖屏画面被拉伸填满横屏窗口的问题）。
- **首次投屏保护链**：`watch()` settleMs 归 0，隐藏窗口一出现就在同一轮嵌入；`embed(..., {show:false})` 先只建父子关系、保持隐藏，给引擎 600ms 自行出首帧；`embedguard.js` 每 200ms 校验父子关系/可见性/几何并就地修复，到点仍隐藏就 `ShowWindow` + `SWP_FRAMECHANGED` + `InvalidateRect`；`nudge()` 不再夹带 `SWP_SHOWWINDOW`，避免抢在保护期前显示；`UxPlayEngine` 加 `started` 事件，自动重启换 PID 后重挂 watcher；`detach()` 按原样式决定是否显示，避免收尾冒出独立窗口。
- 新增 `scripts/test-firstcast.js`（`npm run test:firstcast`）：22 项，含假窗口跑 watch 状态机、embedguard 直接用生产代码、真实 Win32 窗口跑 SetParent/显示/detach 的 FFI 集成。

验证结果：`npm run test:firstcast` 22/22；`npm run check` 12/12；smoke-test「引擎持续运行 + 已检测到 _airplay._tcp 应答」；全量 JS 语法通过；渲染层 30 个元素 id 全部对应、CSS 规则齐全；应用实启日志 `[画面] 嵌入模式 = child（当前窗口内显示），首帧保护 600ms` + 引擎就绪，开启日志后无渲染层异常、无残留进程。真实 iPhone 首次投屏仍需用户复测（D3D12 渲染无法离线模拟）。

经验：从精简旧标签切分支会删掉 master 上跟踪的 runtime/，`git checkout master -- runtime` 再 `git reset -- runtime` 可在保留文件的同时把它们变回被忽略状态，比复制 477MB 更快。
